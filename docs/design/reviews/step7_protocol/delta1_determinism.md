## New findings in the fold's diff

### NIT N1: `tests/test_determinism.py::ASYNC_CLOCK_ALLOWED` exempts a name for a whole file, not the handshake's one use

The allowance is `{"src/simcore/host/server.py": {"wait_for"}}`. The comment says "the host's handshake deadline is the one use". The unit test `test_only_the_handshake_deadline_may_use_the_loop_s_clock` checks only that `sleep` stays banned in that file. I planted `async def _pace2(): await asyncio.wait_for(asyncio.Event().wait(), 0.05)` in the copy's `server.py`, and the scan stayed green. Failure scenario: step 5a puts the simulation lane's hand-off in `server.py` as `await asyncio.wait_for(queue.put(msg), budget)`. Wall time then decides whether an intent reaches the lane. The scan, which claims the handshake as the one use, never sees the second. Round 1 already said a per-file exemption is too coarse here, and a per-file-per-name one is still per file. Fix, unverified: key the allowance by the enclosing function as well (`("src/simcore/host/server.py", "_Host._hello", "wait_for")`, found by walking `FunctionDef` parents), or require exactly one hit.

### NIT N2: no test fails if the main scan stops calling `async_clock_findings`

The parametrized tests call `async_clock_findings` directly. Only `test_the_simulation_and_tests_have_no_hidden_sources_of_nondeterminism` wires it into the scan of `src/`. I deleted the three `hits += [... async_clock_findings ...]` lines in a scratch copy, and all six scan tests stayed green on a clean `src/`. The commit's "an asyncio.sleep planted in the host turns it red" holds today, but nothing keeps it true. Failure scenario: a later refactor of the main test drops the call, and the asyncio scan becomes a unit-tested function that guards nothing. Fix, unverified: give the collector a root parameter, or factor out `scan(root) -> hits`, and test it on a `tmp_path` tree holding one planted `asyncio.sleep`.

### NIT N3: `src/simcore/core/text.py::player_text`: 5,812 code points are accepted on 3.14 and refused on 3.12, and the docstring's "never re-checked" rests on a rule no log reader is held to yet

I measured it. For every scalar value `c`, I ran `player_text("a"+c+"a")` under 3.12.12 (unidata 15.0.0) and 3.14.6 (16.0.0). 3.14 accepts 5,812 code points that 3.12 refuses, which are Unicode 15.1's and 16.0's additions. 3.12 accepts none that 3.14 refuses, so the 16.0 tables never make 3.12 laxer (script: `<scratchpad>/delta1/determinism/cn.py`).

The new docstring says "the text kept is what a replay reads back, never re-checked". That matches boundaries §6.2: `params` are "the typed canonical form after stage 1". But the gate table (§5) puts intent logs and bug reports behind "the strictest gate" on strangers' machines. A speak record logged on 3.14 that holds a Unicode 16 character would be refused if that log reader re-validates speech through `player_text` on 3.12. The environment mismatch in §6.3 only downgrades a replay to an outcome-class check, so it doesn't cover a refusal at load.

Also, `test_the_property_tables_are_sorted_disjoint_ranges_at_unicode_16` asserts `UNICODE_VERSION == "16.0.0"`, a constant in the same tree. That can't fail, and it ties the tables to nothing the interpreter has. This is Trust's T-N6 in measured form. I leave its status to that lens. Fix, unverified: a step-checklist test for the log reader ("a log whose speak holds a Unicode 16.0 character loads on 3.12"), or pin guest text to the oldest supported interpreter's assignments with a table of the 5,812 points.

- **The staleness check's dotfile rule.** `stale()` skips a file whose own name starts with `.`. A file inside a hidden directory is still reported as left over (loud and safe), and a generated dotfile name would always read as stale (loud). The rule is guarded: with it removed, `test_the_generator_reports_a_changed_a_missing_and_a_left_over_file` fails. No tracked file under the fixtures starts with a dot, and Godot reads the fixtures through `manifest.json`, so a hidden file can't change what either reader checks. The one blind spot: a dotfile someone commits there would be invisible to `--check`. Nothing reads such a file, so it is harmless.
